# PolyTrack AI — 阶段 0 可行性验证报告(实测)

目标游戏版本:PolyTrack **0.6.3**(`app-polytrack.kodub.com/0.6.3/`)。环境:云容器 4 核,Node 22,Playwright + 预装 Chromium(无头,软件 WebGL)。
所有数字来自 `logs/` 里的原始日志,可用 `node scripts/run_all.mjs` 复现(T4/T3b 的运行方式见各节)。

## 总结论

| # | 任务 | 判定 | 一句话证据 |
|---|---|---|---|
| 1 | 受控 / 加速运行 | **通过** | 受控下游戏逻辑与未打补丁的真实时间基线**逐帧一致**;浏览器内每帧消息路径 ≈10×,离线 Verify 路径 ≈180×(单 Worker) |
| 2 | 读取状态 | **通过** | 位置 / 速度 / 检查点 / 完成时间直接解码物理 Worker 的状态缓冲区;与 HUD 逐项核对全部一致 |
| 3 | 确定性 | **通过,带一项已知不一致** | 3 个脚本 × 7 种时钟配置,轨迹哈希全部相同;游戏自带 `Verify` 在完成帧为 true、±1 帧为 false。**但**重生压力测试(3.4)发现:实时按键路径下 R 的行为(整局重来 vs 物理重生、回放里 reset 持续多久)随主线程节奏变化;物理 / 回放路径本身不受影响 |
| 4 | 帧精确按键注入 | **通过** | 游戏实际记录的按键翻转帧 == 我们下发的帧;不同步长下结果一致(缩减配置:2 种步长 × 6 个脚本) |

**判定规则**:四项全部通过 => **路线 B(确定性离线搜索)可行**(任务 3 的重生不一致只影响"实时按键"这一层,不影响在回放空间里做搜索)。后续我已经顺着这个结论做了原型(见 `README.md`),
原型的结果见本报告第 6 节。

**两个必须说清的前提**
1. 标准做法"拦截页面里的 rAF / performance.now / Date.now"**不够**:物理跑在独立 Web Worker 里,有自己的时钟。
   必须虚拟化 Worker 的时钟(我是在内存里把垫片拼到 Worker 脚本前面),只改主线程是没用的。
2. 我没有查到官方对 TAS / 机器人成绩的明文规定(speedrun.com 对我的网络返回 403,itch.io 论坛那帖只读到了"作弊可能性"的讨论而非规则)。
   这是**规则风险**,不是技术问题:提交排行榜前请自己去官方渠道确认。本项目的 harness 默认拒绝一切向游戏服务器的请求,实验没有上传任何成绩。

## 1. 任务 1:受控 / 加速运行

**发现的机制**(详见 `phase0_internals.md`)
* 物理:Emscripten C++/WASM,跑在 `simulation_worker.bundle.js` 里,**固定 1000 Hz**(1 帧 = 1 ms,完成时间 = 完成帧数)。
* 实时循环:每次 rAF 累加 `clamp((performance.now()-last)/1000, 0, 0.1)` 秒,`while (acc > 0.001) 步进一帧`。所以单次回调最多追 100 帧。
* Worker 给按键打帧号:`frame = car.frames + max(0, performance.now() - 上次tick时间)`。真实时间下这是**墙钟抖动源**。

**做法**:harness 在内存里把 `worker_shim.js`(虚拟 `performance.now / Date.now / rAF / setTimeout / setInterval`)拼到 Worker 脚本之前;
主线程通过消息 `advance(ms, step)` 驱动虚拟时间。可选再虚拟主线程时钟(不渲染时需要,否则不会发 `StartCar`)。

**实测**(`logs/t1_speed.log`,640×360,软件 WebGL,2 万帧):

| 配置 | 速度 | 与未打补丁基线逐帧比较 |
|---|---|---|
| A 未打补丁,真实时间 | 1.00× | — |
| B1 虚拟 Worker,步长 16.7 ms,渲染 | 10.4× | 相同(5999 帧) |
| B2 步长 100 ms(上限),渲染 | 10.8× | 相同 |
| B3 步长 1 ms(每步一帧),渲染 | 9.0× | 相同 |
| B4 步长 100 ms,1280×720 | 6.2× | 相同 |
| C1 虚拟 Worker + 虚拟主线程,不渲染,100 ms | 10.1× | 相同 |
| C2 同上,1 ms | 9.3× | 相同 |

* 浏览器内的"每帧回传状态"路径瓶颈在 postMessage + 主线程处理,约 10×,**不随步长变化**。
* 要更快:走游戏自带的**非实时路径**(`Init.isRealtime=false`、`Verify`)。`logs/t1b_offline_throughput.log`:
  Verify 60 万帧约 3.2 s => **≈180 000 帧/秒 ≈ 180×**(单 Worker,Worker 数可再乘 4 核)。游戏自带 `testDeterminism()` 返回 `true`。
* 结论:**通过**(速度明显 > 1,游戏逻辑与基线逐帧一致)。要做大规模搜索必须走离线路径,不是"加速浏览器"。

## 2. 任务 2:读取状态

车辆状态不需要 OCR:物理 Worker 每步回传 ≤227 字节缓冲区,我在页面侧包装 `Worker` 旁路解码(字段布局见 `phase0_internals.md` §4):
carId、已执行帧数、车速、flags(是否起步 / 完成 / 能否检查点重生 / 四轮接地)、完成帧数、下一个检查点序号、位置 xyz、四元数、悬挂 / 转向 / 当前按键。
HUD 也是 DOM 文本,可以交叉核对。

**实测**(`logs/t2_state.log`,9 个采样点):时间 / 车速 / 检查点三项与 HUD **全部一致**(车速 HUD 为整数,差 <1);
完成后 HUD 显示的时间 = 状态里的 `finishFrames`(8215)。**通过**。

## 3. 任务 3:确定性

### 3.1 方法
同一份输入脚本,在 7 种运行配置下各跑一遍(虚拟 Worker 步长 100 ms ×3 次、60 Hz 渲染、逐 1 ms、7 ms / 3 ms 奇数步长、真实时间 1×),
对每一帧的 `[帧, x, y, z, 车速, 检查点, 按键, 完成]` 取 sha256 哈希比较;再用游戏自己的两条独立路径复核:
(a)非实时回放路径逐帧对比;(b)全新 Worker 里的 `Verify`,目标帧 = 完成帧(应 true)、完成帧 ±1(应 false)。

### 3.2 结果(`logs/t3_determinism.log`)
| 脚本 | 内容 | 完成帧 | 轨迹哈希 | 7 配置是否相同 |
|---|---|---|---|---|
| S1 | 直路,W 常按,左 / 右点按 | 8250 | `3cb4a4d6…` | **是** |
| S2 | S1 + 7000 帧按 R(检查点重生) | 12585 | `ce4f1881…` | **是** |
| S3 | 第 0 局 3000 帧按 R(无检查点 => 整局重来),新一局重复 S1 | 8250 | `3cb4a4d6…`(与 S1 相同) | **是** |

* 全部配置:回放路径逐帧一致 = true;Verify 在完成帧 = true,±1 帧 = false;全新 Worker 重复 5 次 Verify 全是 true。
* **对照组**(不打补丁,真实时间,用墙钟注入按键):完成帧 8253 / 8347 / 8226(同一脚本),**互不相同,也不等于 8250**——
  这正是"不虚拟 Worker 时钟就不可复现"的直接证据。

### 3.3 重生相关的不一致
* 两种语义(`phase0_internals.md` §6):已过检查点 => 物理重生(同一辆车,回放里记成 1 帧脉冲 `[F, F+1]`,与按住多久无关);
  未过检查点 => 整局重来(新 carId,帧从 0 重算,新一局以当前按住的键开局)。
* S2 / S3 在所有配置下结果一致,说明这两种语义本身是确定的;**坑**在于输入侧:同一帧里 R 的 keydown / keyup 与新一局开局顺序、
  以及"按住 R 多久"对回放是否有影响(没有)——这些需要在驱动器里按语义处理,否则会得到"看起来不一致"的结果。

### 3.4 重生压力测试(`scripts/t3b_respawn.mjs`,`logs/t3b_respawn.log/json`)——**发现了与重生相关的不一致**
三个脚本 × 4 种时钟配置(100 ms 步长 / 逐 1 ms / 7 ms+3 ms 交替 / 60 Hz 渲染),W 一直按住,检查点约在 5558 帧触发:

| 脚本 | 内容 | 结果 |
|---|---|---|
| RS1 | 过检查点后约 40 帧(5600)点按 R,再在 5900、5902(隔一帧)、6600 各点按一次 | **不一致**:3 种配置得到 3 局(R 变成"整局重来"),完成帧 **8215**;`render_60hz` 配置得到 1 局(R 变成"物理重生"),完成帧 **12184** |
| RS2 | 6000 帧长按 R 300 帧并在期间改油门/方向,6500 再点按 | **完成帧相同(12084)**,但游戏**记录进回放的 reset 翻转帧不同**:`[6000,6110,…]`(100 ms 步长、60 Hz)/ `[6000,6001,…]`(逐 1 ms)/ `[6000,6111,…]`(7+3 ms);轨迹哈希因此不同 |
| RS3 | 无检查点时 R(整局重来)后,新一局里 7000、7500 各点按 R | 4 种配置结果完全一致(8215,4 局);**但是 R 并没有变成物理重生**,原因没查清(见下) |

* 所有这些运行里:游戏非实时回放路径与实时路径逐帧一致 = true;Verify 在完成帧 = true、±1 帧 = false。也就是说**物理 / 回放路径本身始终是确定的**,
  不一致出在"主线程怎么把按键事件翻译成控制序列"这一层。
* 我的解释(**推测,没有用代码验证**):
  1. R 是"整局重来"还是"物理重生",取决于主线程**已经收到的最新状态**里有没有可重生的检查点;离检查点很近(RS1:40 帧)时,不同的主线程节奏会让这个判断不同。
  2. 回放里 reset 的持续长度 = 物理重生后到主线程清掉 reset 控制位之间的确认延迟(1 帧 / ~110 帧 / ~111 帧,正好对应各配置的步长节奏)。完成帧不受它影响(RS2),但每帧控制位不同,所以逐帧哈希不同。
  3. RS3 的 R 没有触发重生:我没能确定这是游戏的真实行为还是驱动器的帧->局映射问题,**未解决**。
* 对路线 B 的含义:搜索在"回放 / 逐帧控制序列"空间里做(`Verify` / 自建 `Eval` 路径),不经过主线程的按键翻译,所以不受这个不一致影响;
  但是**不要把"实时按 R"当成可复现的输入**。阶段 1 如果要利用重生,要把 reset 作为回放里显式的翻转帧,并用游戏自带 `Verify` 逐个校验;
  我的原型目前**没有使用重生**。

## 4. 任务 4:帧精确按键注入

**做法**:按物理帧号注入真实键盘事件(CDP)。驱动器闭环:批量推进到目标帧前,再用 1 ms 单步精确停在帧 F,下发 keydown / keyup,
往返确认后继续。虚拟时钟冻结时,Worker 给按键打的帧号恰好等于当前已执行帧数。游戏对 `isTrusted` 没有检查。

**判据**:游戏**自己记录**的回放(按键翻转帧列表)必须与我们下发的帧逐帧相同;不同步长下完成帧 / 轨迹哈希相同;游戏非实时回放路径与实时路径一致。
**结果**(`logs/t4_injection.log`,缩减配置 `QUICK=1`:虚拟步长 100 ms 与逐 1 ms 两种;6 个脚本):

| 脚本 | 内容 | 记录翻转帧 == 下发帧 | 两种配置哈希相同 | 回放路径一致 | Verify |
|---|---|---|---|---|---|
| S1 | W 常按 + 左右点按(5 个事件) | 是 | 是(`3cb4a4d6…`,完成 8250) | 是 | 完成帧 true |
| S2 | S1 + R(7 个事件) | 是 | 是(`ce4f1881…`,完成 12585) | 是 | 完成帧 true |
| E1_edge | 1 帧点按、连续两帧换键(左抬同帧右按)、同一帧两个键、油门只松开 1 帧(11 个事件) | 是 | 是 | 是 | — |
| R1 / R2 / R3 | 三组随机种子,各约 200 次随机翻转 | 是 | 是 | 是 | — |

**判定:通过**——按键能落到指定的物理帧,游戏自己记录的回放与下发序列逐帧相同,同一序列在不同时钟节奏下得到逐位相同的轨迹。

* 限制 1:原本设计的是 4 种配置(再加 60 Hz 渲染、7 ms+3 ms 交替),全量运行在软件渲染下超过 25 分钟且与其他实验抢 CPU,我把它终止了,只报告缩减版;
  这两种配置在任务 3 里已经对 S1–S3 跑过(结果一致)。
* 限制 2:E1 / R1–R3 在 6000 帧内没有冲线(没给油门或路线随机),所以没有 Verify,只比较翻转帧和哈希。
* 限制 3:**含 R 的随机脚本**这里没有出现不一致,但任务 3.4 的专门压力脚本(RS1/RS2)出现了——见 3.4,原因是 R 的语义依赖主线程状态,不是帧注入本身不准。
* 另:对"从游戏里把 CDP 键盘事件送进去"这一步,游戏不检查 `isTrusted`;1 帧点按在虚拟时钟冻结的前提下是可靠的,真实时间下做不到(见任务 3 对照组)。

## 5. 遇到的问题(按出现顺序)
1. `--use-gl=swiftshader` 参数反而让 WebGL 失败 -> 用 Playwright 默认启动即可。
2. 只虚拟 Worker 时钟、不虚拟主线程时,不渲染的配置里车永远不起步(`StartCar` 由主线程 rAF 循环发出)-> 首次按键后给主线程补 tick。
3. HUD 文本正则会把"0/1"与车速粘在一起、把检查点分段时间当成当前时间 -> 改成按 DOM 结构解析;完成后 HUD 冻结而物理仍继续,所以完成后用 `finishFrames` 比对。
4. `Verify` 遇到回放反序列化失败时 Worker 抛异常、页面永远等不到结果 -> 加 error 监听 + 超时。
5. S3 卡死:无检查点时 R 会**立刻新建一辆车**,驱动器还盯着旧车 -> 追踪最新车,事件带 `run` 字段,R 要按住到新一局开始之后再松。
6. 非实时回放路径返回 0 行:WASM 是异步初始化,虚拟 tick 在初始化前被吃掉 -> 回放循环里加真实时间 sleep。
7. 官方 Summer 1(679 个部件,多层)起点到终点在我的"道路格子 BFS"里不连通,所以阶段 0 没拿官方赛道做完赛实验;
   改用**游戏自己的序列化器**生成了我们自己设计的直线赛道(`scripts/build_mini_track.mjs`)。
8. 完整 T4(6 个脚本 × 4 种配置,含 1 ms 单步)在软件渲染下太慢(>25 分钟),且与别的实验抢 CPU,被我终止;最终报告里的 T4 用缩减配置(见第 4 节)。

## 6. 阶段 1 建议 / 原型结果
既然四项都通过,我没有停在可行性上,而是顺着路线 B 做了一个能端到端跑通的原型(代码与用法见 `README.md`)。

### 6.1 原型做了什么
* **批量评估引擎**:在内存里给物理 Worker 加了几条消息,直接调用游戏 `Verify` 内部用的"创建车 / 步进一帧"函数,一批控制计划并行发给 N 个 Worker;
  还能对 WASM 线性内存做**快照 / 恢复**(20 MB,几毫秒),所以可以"从某个状态出发评估一批后续计划"。
  自检(`test/engine.test.mjs`,5 项全过):Eval 的完成帧 = 阶段 0 参考值 8250 且游戏 Verify 通过、±1 帧失败;结果与 Worker 数无关;
  整段模拟 = 前半段提交 + 后半段从快照出发(逐比特);可变时长动作 = 逐帧展开;`reset` 回到起点后重算逐比特相同。
* **搜索**:阶段 A 滚动时域 CEM(近处动作 40 帧、远处 100 / 240 帧,总时域 ≈ 1.8 s;评分用沿中线进度 + 速度项 − 偏离 − 切换;全员掉出赛道时回退重规划);
  阶段 B 窗口爬山(快照到窗口起点、批量变异窗口、再整圈精确验收,完成帧不变差才接受)。
* **校验与输出**:游戏回放串(`out/*.recording.txt`)、JSON、HTML 报告;每个结果都过游戏自带 `Verify`(完成帧 true、±1 帧 false)。

### 6.2 实测结果(自制蛇形赛道:6 个 S 弯,中线约 1.1 km,`scripts/data/slalom.txt`)
| 方案 | 圈速 | 说明 |
|---|---|---|
| 一直按住 W | **不能冲线** | 第一个 S 弯就冲出路面,中线进度 244 m |
| 第一版规划(7 个动作,时域 2.3 s,固定种子 1) | 19.010 s | 再做整圈随机变异爬山(旧版,已被窗口版取代)→ 18.662 s,窗口爬山 → 18.654 s |
| 4 个动作 + 变时长时域(40×6, 100×6, 240×4 帧)+ 掉出时回退重规划,种子 1(**当前默认参数**,最佳结果 `out/slalom_v3.*`) | **16.838 s → 16.835 s** | 规划阶段 ≈ 290 s(4 核,且与另一个实验抢 CPU),Verify 通过 ×3,±1 帧均为 false;另用 `scripts/verify_result.mjs` 独立复核通过 |
| 同上 + "速度骤降"惩罚(`--crash 60`) | 17.166 s → 17.161 s | 没有再触发回退,但速度曲线上仍有两次撞击(≈8 s、≈11 s);**惩罚并没有让规划器避开撞击** |
| 同上 + 更长的远端时域(40×6, 100×6, 240×2, 480×2)+ 撞击惩罚 | 20.566 s → 20.534 s | **更差**:调参很脆弱,没有按直觉改善(这次的输出文件没有保留,只有数字) |

* **可复现**:换了几处代码修订之后,用当前代码和默认参数重跑(`out/slalom_v6.*`,打磨只给 30 s)得到同样的规划结果 16838 → 16835、同样的 7 次回退(**圈速相同,但回放串不是逐字节相同**:按时间停止的打磨会接受若干"完成帧不变"的中性变异,次数随预算而变)。要逐字节可复现请用 `--polish-iters N` 按迭代数停止;`test/solver.test.mjs` 验证了这种口径下同种子两次运行的回放串逐字节相同(小赛道)。
* 粗略参照:同样 1.1 km 如果是一条直路,按阶段 0 实测的加速曲线约 13.7 s(8 s 跑 ≈497 m,之后 ≈108 m/s)。当前结果比这个"不转弯的理想"慢约 23%;**真实最优未知**。
* **规划阶段会翻车**:第一次用当前参数跑时,在约 16 000 帧处所有候选都掉出赛道;加了回退重规划后同一赛道回退了 7 次才通过(日志 `out/slalom_v3.log`)。这说明评分函数对高速入弯不够谨慎。
* **最终结果里仍含一次撞击**:HTML 报告的速度曲线在约 13 s 处从 ≈340 km/h 骤降到 ≈170 km/h 再恢复。回退重规划只是"没掉出赛道",并没有避免撞击——
  规划时域(≈1.8 s,≈150 m)看不到足够远的弯,来不及提前减速。也就是说 16.8 s 离这条赛道的真实水平还有明显差距(撞击大约吃掉 2~3 s)。
  这是阶段 1 的第一优先级修复项。上面两个调参实验说明:简单加惩罚、简单拉长时域都**不能**解决问题(见表),需要更结构化的做法(见 6.3 第 2 条)。
* 打磨阶段增益很小(16.838 → 16.835)。按键时间线抖动很多(HTML 报告里能看到),离"人能复现的干净输入"还很远。

### 6.3 阶段 1 建议(按优先级)
1. **官方赛道的进度势能**:现在的"道路格子 BFS 中线"假设单主路。官方 Summer 1 是 679 个部件的多层赛道,起点到终点在我的 BFS 里不连通。
   方案:按检查点 / 终点序列分段 + 3D 邻接(含坡道 / 跳跃)的距离场,或用一次"能跑完的参考圈"自举出中线。这是上官方赛道的第一道门槛。
2. **提高搜索质量**:先解决上面的撞击——加惩罚、拉长时域我都试过,没用;更可能有效的是给每个弯一个"入弯速度上限"(由中线曲率 / 偏移量推出,或用一次试跑标定),再让规划器在上限内追速度;CEM 采样噪声大;换成带快照的束搜索 / 树搜索(快照已验证可用),特征里加入航向误差、侧滑、车轮接地数,避免高速入弯翻车;
   打磨阶段加入"清除抖动"的简化步骤(在完成帧不变差的前提下合并短脉冲)。
3. **成本控制**:单次整圈评估约 50~120 ms/Worker;可以用多进程多浏览器页面(每页 4 Worker)横向扩展;规划阶段时域和种群大小决定总耗时。
4. **重生(R)**:先在回放里把 reset 当成显式翻转帧来评估(`Verify` 校验),再决定要不要让搜索使用它;不要走实时按键路径(见 3.4)。
5. **规则**:提交任何成绩前先确认官方 / 社区对 TAS 与机器人的规定(见总结论第 2 点),并搞清楚排行榜服务端是否重放校验。
6. **版本固定**:Worker 补丁依赖 0.6.3 的压缩布局,锚点变了会直接抛错;每次游戏更新都要重跑 `test/engine.test.mjs`。

### 6.4 官方 Summer 1 的尝试(后续跟进)
**为什么之前连不通**:Summer 1(679 个部件)的路线是 起点(64,11,4)→检查点 0→检查点 1→检查点 2→终点(-60,4,56),终点所在的 y=4 平台在"道路格子"图上与主路之间隔着约 5 格(25 m)的缺口(需要跳过去),
而且检查点 2 在检查点 1 之后要折返——按"到终点的最短距离"算势能,检查点 1 的势能(99)反而比检查点 2(122)低,会让车绕过检查点 2 直奔终点。

**做法**(`scripts/lib/progress.mjs: buildProgressField`):按检查点顺序把赛道分成 4 段(起点→C0→C1→C2→终点,长度 160 / 360 / 161 / 565 m,总计 1246 m),
每段以该段目标为源在可行驶格子(类别 0–5)上做 Dijkstra,连续邻接代价 5 m/格,另加"跳跃边"(水平 ≤6 格、层差 ≤5 格、代价 ×1.5);
车在第 k 段(用状态里的 `nextCheckpointIndex`)位于格 c 时,进度 = 前 k 段长度 + (第 k 段长度 − dist_k(c))。构建 0.6 s,2000 次查询 11 ms。单元测试里用带缺口的合成赛道验证了跨缺口建图与跨检查点的连续、单调。

**结果:没有跑通。** `node scripts/solve.mjs --official --potential field …` 的三次尝试(日志 `out/summer1_*.log`,失败现场 `out/summer1_*.failed.json`):
| 尝试 | 结果 |
|---|---|
| a(默认惩罚) | 车从 y=55 的起点处滑下去、过了检查点 0 和 1,然后在检查点 2 之前(进度 631 / 1246,约 51%)停滞约 20 s,规划器耗尽 45 000 帧上限而失败 |
| b(同 a,加了"停滞看门狗"以快速失败) | 同样在进度 631 处停滞(位置 x=−107.1,y=0.1,z=−29.4,车速 ≈14 km/h)——位置在通往检查点 2 的窄路入口处 |
| c(放宽离路面惩罚:`--half-width 4 --off-penalty 3`) | 更早就失败:车在约 14 000 帧时冲出路面、悬空在 y≈47 |

**对停滞的诊断**(用 `b` 的失败现场,从停滞状态出发试了几个简单控制):车并没有被卡死——按 W 能继续向 +x 开,W+左 能转向 −z(向检查点 2 的方向),先 S 再 W 也能动。
所以问题在**规划器**:停在窄路口、朝向不对,需要低速掉头 / 倒车再进,而当前的 CEM(时域 ≈1.8 s、离路面惩罚较大、评分只看进度 + 速度)找不到"先退一点再转"的计划,所有候选评分几乎相同,就原地蹭。
放宽离路面惩罚(c)则让它早早冲出路面。这是**推测**:我没有去逐帧确认碰撞对象。

**结论**:进度势能(多层 / 跳跃 / 检查点折返)这一道门槛已经过了——Summer 1 能建出连贯、单调的 4 段势能,规划器也顺着它走过了检查点 0 和 1。
卡点转移成了规划器本身:需要能做低速机动(掉头 / 倒车)的搜索,例如在滞留时切到更细的动作集(含 S、单独转向)+ 更长的近端时域,或在入窄口前给出"入口朝向 / 速度"的子目标。我没有继续往下做。
